# Phase 4 — Security & Collaboration: plan and status (started 9 Nov 2026)

**Status: every bindable requirement Verified; completion awaits the owner's decision on MAL-060 and MAL-069** (unbound, with their gaps below). Phase 4 is marked COMPLETED only after that decision.

Master Spec v2, Milestone 4 (Security & Collaboration) covers encryption, redaction, signatures, compliance validation, comments, document versions and access controls. Those are the review and collaboration requirements MAL-056 – MAL-060, and the security and compliance requirements MAL-061 – MAL-070.

## Acceptance rule

This is the same rule as Phases 2 and 3. A capability becomes RELEASE_READY only through `src/suite/commands/verifiedCommands.ts`. Its binding must meet all of these:

- Every clause of the requirement text has passing checks.
- Those checks drive the real UI, save the result, and reopen it independently, with PDF.js, pdf-lib, OpenSSL or pyHanko as appropriate.
- They run in CI.
- The PR has a clean review.

Requirements that cannot honestly meet their text stay unbound, with the gap stated.

## Judgement calls

1. **MAL-070, what "removed" means.** Sanitize deletes every object that is no longer referenced before saving. Before this, pdf-lib would still have written them into the file. The fix covers Sanitize and Redaction, and is proven by a byte-level test that fails without it.
   - Hidden text is removed only when a whole text object is invisible.
   - Off-layer content is removed only when its marked-content block is balanced.
   - Anything that cannot be removed safely is reported as kept.
2. **MAL-064 is rule-based, not a learned model.** Detection runs on the device. It uses:
   - patterns, with check digits: Luhn for cards, mod 97 for IBANs, Verhoeff for Aadhaar;
   - label and title cues and a common-given-name list for names;
   - street and postcode patterns for addresses;
   - your own phrases and `/patterns/`.

   The spec asks to "privately detect candidate … for user-reviewed redaction", and every candidate is reviewed before it is marked. Scanned pages need OCR first.
3. **MAL-068 is a condition checker, not a certified validator.** It checks the conditions it lists for PDF/A-1b, 2b and 3b, PDF/X-1a and 4, and PDF/UA-1, and says so in the UI and in the report. Full conformance still needs veraPDF or an equivalent.
4. **MAL-056.**
   - Threads, replies and resolution go into the PDF as standard annotation replies (IRT) and review states.
   - Mentions are `@name` in a comment.
   - Notifications are shown to that person when they open the PDF in MALENJO. Nothing is sent over a network.

   The owner is asked to confirm that this reading of "notifications" is acceptable.
5. **MAL-066.** This is a file-based signing workflow:
   - recipients and their order are stored in the PDF;
   - each recipient signs with MAL-065 in turn;
   - the status is worked out from the signatures actually present;
   - the PDF carries an embedded audit log, plus a completion report.

   Delivering the file to the next recipient is up to the sender, because MALENJO sends no email.
6. **MAL-065 file formats.** PKCS#12 files must use AES (PBES2), which is what current OpenSSL, Windows and macOS export. Legacy RC2 or triple-DES files are refused with advice to export them again. Timestamp and CRL requests:
   - in the desktop app, go through a restricted native command (http/https only, size and time limits);
   - in the browser, use `fetch`, which needs the timestamp authority to allow cross-origin requests.
