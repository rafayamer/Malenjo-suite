- Every clause of the requirement text has passing checks.
- Those checks drive the real UI, save the result, and reopen it independently with PDF.js and pdf-lib.
- They run in CI.
- The PR has a clean review from Claude and from Codex.

## Slice 3.1 — Forms (MAL-046 – 050, 052, 053)

### Engine: `src/suite/pdf/forms/`

**`formDesign.ts`** creates, lists, moves and resizes, renames and deletes AcroForm fields:
- Field types: text, number, date, check box, radio group, dropdown, list box and unsigned signature placeholders.
- Fields are placed from rectangles drawn on the page as shown, for any page or view rotation.
- Widgets get `/MK /R`, so appearances are drawn upright on rotated pages.
- Radio buttons carry their label in their own appearance, so a label moves with its button.
- Choices store export values and labels as `/Opt` pairs; the appearance shows the label.
- Signature placeholders hold a `/Lock` (`SigFieldLock`) with All, Include or Exclude.
- Signed or certified documents are refused.

**`formLogic.ts`** writes the logic as standard Acrobat form scripts:
- `AFNumber_Format`/`Keystroke`;
- `AFDate_FormatEx`/`KeystrokeEx`;
- `AFRange_Validate`;
- `AFSimple_Calculate`;
- a pattern check;
- a `display.visible`/`display.hidden` toggle.

It also orders `/CO` by dependency and refuses cycles. It reads these statements back with exact patterns only, and evaluates them itself.

**`formFill.ts`** fills a form with its logic applied:
- Every validation problem is reported, and the fill is refused until they are fixed.
- Calculated values are written.
- Number and date fields keep the raw value in `/V` and show formatted text in the appearance.
- Fields hidden by a rule get the Hidden widget flag.
- Appearances that a reader would otherwise have to draw (choice labels) are drawn.

It also flattens all fields or chosen ones into page content. Hidden widgets are dropped. A field that another remaining field depends on is refused.

**`formData.ts`** exports and imports CSV (`name,value` rows, or a header row of names), JSON, FDF and XFDF:
- Import matches full field names and accepts labels in place of export values.
- It reports unknown names, and skips read-only and calculated fields.
- XFDF with a DOCTYPE or ENTITY is refused.

### UI

- **Forms → Design form…** (`PdfFormDesignerPanel`):
  - Pick a type and its settings, choose **Place on the page**, then drag.
  - Click a field's outline to select it.
  - **Move or resize by dragging**, rename, edit properties and logic, or delete.
  - Per-field settings reset after each placement; the type and number/date format carry over.
- **Forms → Fill form…** (`PdfFormFillPanel`):
  - Live calculation, visibility and per-field errors. **Save values** is disabled while any error remains.
  - Flatten selected fields or all fields.
  - Export and import CSV, JSON, FDF and XFDF.

### Judgement calls (flagged for the owner)

1. **MAL-050 "sandboxed supported JavaScript actions".** MALENJO does not execute document JavaScript at all. The supported actions are the standard AF functions listed above, written so other readers apply them. MALENJO recognises them by exact pattern and evaluates them in its own code. Any other script is kept in the file, listed in the designer as "not run", and never executed. This is stricter than a JS sandbox, and it is the safe reading of "sandboxed supported".
2. **MAL-049** creates signature *placeholders* and their properties (tooltip, required, lock list). Applying a digital signature belongs to the signing requirements.
3. **MAL-053 "where applicable".**
   - Signature and push-button fields have no data to exchange and are left out.
   - CSV multi-selections are repeated `name,value` rows.
4. **Formatting.** Values are stored raw (as readers do), and the formatted text appears in the appearance stream. Flattening therefore shows the formatted value, for example `$1,250.50`.
