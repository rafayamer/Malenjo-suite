# Source-truth audit — UI 53.6 left navigation rail and panel

## Controlling source

Canonical artifact:

- `MALENJO_SUITE_FINAL_MASTER_README.md`
- SHA-256: `e24c8f238c01bfd455f2d9994789feaa5b674ac167d191e678452fc3cf5b13aa`
- Relevant section: **53.6 Left navigation rail and panel**
- Canonical lines in the archived source: **4166–4185**

This audit covers only the left-edge navigation structure required by UI §53.6. It does **not** declare bookmarks, PDF optional-content layers, attachment extraction, signing, comments, search, the right inspector, or the wider PDF feature tree complete.

## Source-truth acceptance criteria

For this coherent requirement MALENJO must provide:

1. a narrow left icon rail plus an expandable document panel;
2. an icon-rail width in the canonical 52–64 px budget;
3. an expanded document panel in the canonical 200–260 px budget;
4. PDF navigation entries for Pages/thumbnails, Bookmarks, Attachments, Layers/Optional Content Groups, Signatures, Comments and persistent Search results;
5. suite-level navigation at the application/workspace level rather than consuming the document canvas;
6. a user-controlled collapse path so the document canvas can reclaim horizontal space;
7. honest availability states where a nested PDF feature is not yet implemented, rather than fake operational controls.

## Audit of `main` before this PR

Already present:

- a MALENJO-owned application sidebar at the workspace level;
- a PDF three-pane layout with page thumbnails, central canvas and right inspector;
- operational page thumbnails and multi-page selection;
- operational local PDF text search;
- operational PDF comment creation;
- operational PDF attachment embedding;
- AcroForm inventory that can identify existing signature fields.

Gaps against §53.6:

- the application sidebar was fixed at 238 px and could not be collapsed;
- the PDF left edge was only a 154 px thumbnail column rather than a narrow icon rail plus expandable panel;
- PDF navigation did not expose the canonical Bookmarks, Attachments, Layers, Signatures, Comments and Search panel set;
- search, comments and attachment actions were mixed into the right inspector instead of being available through the left navigation model;
- there was no explicit compact state for maximizing document-canvas width;
- unsupported nested PDF features had no source-truth navigation slot or honest availability state.

## Changes in this PR

### Application/workspace navigation

- adds a user-controlled collapse toggle for the MALENJO suite sidebar;
- collapsed suite navigation uses a 60 px rail;
- full module names remain available through accessible labels/tooltips;
- the expanded application navigation remains the single suite-level navigation system.

### PDF document navigation

- adds a 58 px PDF icon rail and a 224 px expandable panel;
- adds the exact canonical PDF panel set:
  - Pages;
  - Bookmarks;
  - Attachments;
  - Layers;
  - Signatures;
  - Comments;
  - Search;
- selecting an icon opens the corresponding panel;
- the panel can be collapsed independently, leaving only the compact rail;
- Pages keeps the existing operational thumbnail/page-selection behavior;
- Search keeps the existing local search workflow and persistent result list;
- Comments keeps the existing real PDF `/Text` annotation authoring path;
- Attachments keeps the existing embedding action;
- Signatures reports existing AcroForm signature fields from the current form inventory;
- Bookmarks and Layers deliberately expose an honest unavailable state because their discovery/editing providers are separate PDF requirements not yet implemented on `main`.

## Deliberate scope boundary

This PR does **not** implement bookmark discovery/authoring, optional-content group manipulation, existing-attachment inventory/extraction, or full signing UX. Those are nested PDF capabilities with their own source-truth requirements and must not be falsely marked complete merely because §53.6 requires their navigation locations.

No Adobe/Foxit code, icons, artwork or trade dress is copied. The rail/panel implementation is original MALENJO shell/UI code using the project's existing Lucide dependency.
