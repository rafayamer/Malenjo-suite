# MALENJO PDF — Stirling tool parity evidence register

The machine-readable source of truth is [pdf-stirling-parity-matrix.json](./pdf-stirling-parity-matrix.json). Its 90 operation identifiers were transcribed in order from the October 8, 2026 MALENJO development handoff (§5A–5G), **not** independently re-audited against a newer upstream release. The upstream comparison baseline is `Stirling-Tools/Stirling-PDF@25220cbdbde2d526cebf173b94357884e180b8c1`.

**No operation is credited as complete.** Forty-eight locally implemented/native-operation foundations plus nineteen separately source-audited **provider-dispatch-only** workflows are classified **`partial`** (67 total); 23 others remain **`null` (not yet source-audited)**. A provider-dispatch partial means the exact POST route, UI selector, capability gate and response validation are wired; it does **not** mean the PDF processing is implemented, produces valid real output on Windows, or has parity with upstream. This is not a claim of Windows/provider end-to-end verification. For every tool, verify the real MALENJO code, UI command, actual local Windows execution, source license and notices, positive/negative fixtures and golden tests, memory/size limits, and export/save/reopen outcomes; then set a supported status: `implemented`, `partial`, `unavailable`, or `excluded-by-license`. Exclusions need user approval.

## Source-backed endpoint audit — pinned commit

The pinned upstream file `testing/endpoints.txt` at `Stirling-Tools/Stirling-PDF@25220cbdbde2d526cebf173b94357884e180b8c1` has **62 distinct smoke-test endpoint paths** (upstream file blob `1df2e53e690bcd4ca763f88d4d7fb5257c2d0a64`). A byte-for-byte snapshot lives in [pdf-stirling-pinned-endpoints.txt](./pdf-stirling-pinned-endpoints.txt).

Of the **90 handoff requirements**, **54 have an explicit path in that pinned endpoint-test list** and **36 do not**. There are **8 endpoint-test paths** not mapped to the handoff's tool IDs (six filters, PDF decompression, and ebook-to-PDF). These numbers measure *textual route coverage only*, not tool implementation, licensing approval, or user-facing functionality. For the 36 without a route, inspect upstream frontend/composite flows or alternate OpenAPI paths before calling anything absent.

A separate second pass compared the same 90 handoff items against the pinned upstream **frontend** `frontend/editor/src/core/utils/urlMapping.ts` (105 URL aliases, blob `67328c8ab22e775d544c8910387a37aec962628d`) and its `types/toolId.ts` core registry (61 core tool identifiers, blob `de647e2b6e91c6bb9fb66735fd5db748adf75a88`). A pinned [frontend route mapping snapshot](./pdf-stirling-pinned-frontend-routes.json) is included. Of the 36 items without a tested backend endpoint, **22 match an upstream core frontend route**. A third pass located **8 actual Java controllers** (four form handlers, timestamping, standards verification, scanner effect, and pipeline handling), leaving **6 conversion items found only in upstream endpoint configuration**. Some of the frontend items are navigation/documentation links or composite conversion surfaces, not individual backend operations. These results are source *classification*, not functional test completion.

The local PDF tools panel now cross-references the 90 items with **live** provider OpenAPI operation paths: `provider-not-loaded`, `not-in-live-openapi`, `provider-disabled`, or `provider-reports-available`. The final state means only that the local capability resolver advertises availability, **not that any document was processed, saved, reopened or validated offline**. No tools are assigned the evidence status `implemented` by this operation.



### Controller-only and configuration-only evidence

The Java source was checked against the same pinned commit. In addition to the 54 routes present in `testing/endpoints.txt`, eight other routes are declared by concrete controllers: `/api/v1/form/fields`, `/api/v1/form/fill`, `/api/v1/form/modify-fields`, `/api/v1/form/delete-fields`, `/api/v1/security/timestamp-pdf`, `/api/v1/security/verify-pdf`, `/api/v1/misc/scanner-effect`, and `/api/v1/pipeline/handleData`. These can be matched against a **live** OpenAPI response, but are not counted as already passing functional tests.

The last six conversion operations (`pdf-to-epub`, `pdf-to-vector`, `pdf-to-json`, `pdf-to-rtf`, `json-to-pdf`, `vector-to-pdf`) appear only as groups or alternatives in pinned `app/common/.../EndpointConfiguration.java` within this audit. That is **configuration evidence only**. These operations must remain disabled/unknown unless a reviewed runtime handler is separately confirmed.

**Offline caveats from upstream source:** `TimestampController` contacts a remote RFC 3161 timestamp authority; `VerifyPDFController` uses a veraPDF service whose Windows redistribution has not been verified; and `PipelineController` is conditionally excluded in `STIRLING_PDF_TAURI_MODE`. MALENJO's provider capability gate explicitly prevents all three from being advertised as verified offline operations. These do not meet the user's full-functionality requirement.

**Pinned source classification of all 90:** 54 endpoint-fixture routes + 8 controller-only routes + 22 frontend-only entries + 6 configuration-only entries. **Actual function status is 37 partial / 53 unaudited; 0 complete.** Source classification cannot substitute for operation fixture execution.

## Runnable, local-only PDF utilities added to the panel

An open PDF can now be exported without starting the Java Stirling sidecar:

- **PDF information → JSON**: uses MALENJO's new bounded `src/suite/pdf/pdfInfo.ts` reader to report metadata, page count, page dimensions and rotation. Tests in `pdfInfo.test.ts` cover real PDF output, byte preservation, malformed input and oversized metadata. This is **partial** parity with upstream `get-info-on-pdf`: security/signatures, full resources and permission diagnostics are not equivalent.
- **Selectable text → TXT**: reuses `src/suite/pdf/textExport.ts`, the existing PDF.js worker and tested per-page limits. Rejects scanned/image-only PDFs without an OCR layer rather than silently exporting an empty document. This is **partial** parity with upstream `pdf-to-text`.
- **Split by page count → ZIP**: adds `src/suite/pdf/splitByPageCount.ts` with real PDF page copy, per-file reopen/page-order verification, ZIP output and explicit limits. The Organize panel offers this native offline fallback independently of Java. Signed PDFs and AcroForm documents are refused rather than risking invalid signature/form relationships. **Only page-count splitting is available in this fallback**, not size-based splitting, so `split-by-size-or-count` remains **partial**. The in-app download bridge caps ZIP size at 32 MB pending efficient binary streaming.
- **Edit standard PDF metadata**: uses `src/suite/pdf/pdfMetadataEdit.ts` and `pdfMetadataEdit.test.ts`. Prefills the four conventional PDF Info fields (title, author, subject and keywords), bounds metadata length, declines signed documents and invalid inputs, and reopens output to validate the page count and changed fields before applying it via MALENJO's working-copy/Undo route. It intentionally does **not** claim to sanitize XMP/custom metadata or preserve digital signatures. This is **partial** parity with upstream `update-metadata`.
- **Modify or delete AcroForm fields**: existing `src/suite/pdf/formManagement.ts`, its real-file tests, and the existing PDF form inspector now receive explicit evidence links in the 90-tool register. The fields' required/read-only flags can be modified, and selected fields/widgets can be removed with XFA/signature refusal. These are **partial** `modify-fields` and `delete-fields` coverage, not full upstream batch/field-type parity.
- **PDF → structured XML**: `pdfToXml.ts` implements a bounded selectable-text XML export using local PDF.js extraction, page geometry, PDF Info metadata and bookmark titles. XML-sensitive characters are escaped and image-only files without an OCR layer are refused. Graphics, images, full reading order, annotations and XMP are not converted. Clean offline Windows output acceptance remains outstanding. This is **partial** `pdf-to-xml` parity.
- **PDF → structured JSON**: `pdfToJson.ts` uses MALENJO's local PDF.js text extraction and `pdfInfo.ts` metadata/page geometry, with bookmarks, page-indexed text, text-fragment and output-size bounds. Scanned PDFs without selectable text require OCR first. This is an actual local export path exposed in the PDF tools panel, but **partial** parity for configuration-only `pdf-to-json`: images, full graphics, XMP, PDF object structures, annotations and exact layout are not reproduced. Clean Windows save-and-reopen acceptance remains outstanding.
- **Remove review/markup annotations**: the existing selected-note deletion in `src/suite/pdf/review.ts` has been supplemented with `src/suite/pdf/pdfAnnotationCleanup.ts` and four real PDF tests. The user can remove all common review/markup subtypes and related popups from the current working PDF through an undoable command. Form widgets, links, other interactive annotations and file attachments are preserved; signature dictionaries are refused. This is **partial** `remove-annotations` coverage—not signed-document rewriting, secure sanitization, or every upstream subtype.

Both use the MALENJO local save implementation and carry the same Windows final-output verification gate as other tools. Neither sends the PDF to an internet service. The buttons remain usable even when the Java provider is stopped.

- **PDF → Markdown / HTML / page-indexed CSV**: `pdfTextFormats.ts` and `pdfTextFormats.test.ts` add three local selectable-text conversion pathways exposed in Local PDF tools. Markdown and HTML guard against executable markup; CSV neutralizes spreadsheet formula prefixes. The conversions reuse bounded PDF.js text extraction and refuse textless scans without OCR. These are **partial** parity: Markdown does not infer headings/tables/images, HTML does not reproduce positioned graphics/resources, and CSV is page-indexed text rather than table recognition. Clean standalone Windows save/open acceptance is pending.

- **PDF → CBZ comic book**: `pdfToCbz.ts` creates an ordered ZIP of actual PDF.js-rendered page PNGs, checks each extracted image with the bounded PNG decoder and caps output at 32 MB, at most 50 pages. It is **partial** `pdf-to-cbz` parity because rasterization drops text selection/vectors/forms and final physical Windows comic-reader acceptance remains outstanding.

- **PDF → Word DOCX, OpenDocument ODT and RTF**: `pdfOfficeText.ts` and corresponding tests supply three offline container/text conversions based on selectable PDF text, WordprocessingML/OpenDocument package parts and escaped RTF text. They preserve page breaks and Unicode while refusing textless scans, malformed XML, excessive data and source changes. They remain **partial** because DOCX/ODT/RTF fidelity to PDF layout, tables, graphics and styles is missing and installed Windows Word/RTF reopen acceptance is outstanding.

- **PDF → EPUB 3 (reflowable)**: `pdfToEpub.ts` produces a five-part standards-oriented EPUB Open Container Format archive (first uncompressed mimetype, package manifest/spine, navigation and escaped XHTML page text), with output verification and invalid-input tests. It remains **partial**: no reconstruction of images, complex reading order, embedded fonts or Calibre-equivalent layout, and no Windows EPUB-reader acceptance.

- **Auto-rename PDF (metadata-title fallback)**: `pdfAutoRename.ts` generates Windows-safe PDF copy names from the existing PDF Info title, without changing the document bytes or overwriting the working copy in memory. It refuses missing/unsafe titles and files above 32 MB. It is **partial**, not content-aware/OCR title extraction, and requires a clean Windows save/reopen acceptance run.

- **JSON → searchable PDF (text report)**: `jsonToPdf.ts` formats validated UTF-8 JSON onto bounded PDF pages using pdf-lib, converts non-ASCII characters to reversible Unicode escapes, and reopens output in real PDF tests. The React Convert workspace accepts local JSON files; native-only, no network or Java. It remains **partial** because this is text/report pagination rather than structured visual object rendering or arbitrary Stirling schema conversion, with installed Windows acceptance outstanding.

- **CBZ comic → PDF**: `cbzToPdf.ts` extracts bounded image-only CBZ ZIP archives, validates PNG/JPEG integrity, natural-sorts numbered filenames, embeds images in real pdf-lib pages and verifies the saved PDF can be reopened. It rejects ZIP path traversal, archive overexpansion and damaged raster inputs. This is **partial** full upstream parity: limited supported image formats, no comic metadata or text reconstruction, Windows installer acceptance pending.

- **Nineteen existing batch provider workflows now source-audited:** `pdfTwentyWorkflows.ts` carries twenty exact pinned POST-route selectors, React batch buttons, capability gates and generic negative output fixtures; `pdf-to-csv` was already tracked as a native partial. The other nineteen are now tracked as **provider-dispatch partial** without claiming local algorithm implementation or Windows acceptance. The full release gate remains blocked for each one until live Windows output, per-route parameters, save/reopen and licensing are verified.

- **Unlock PDF forms**: `formUnlock.ts` adds a local, bounded AcroForm-only read-only field flag remover; it reopens the modified PDF, verifies all fields are editable and integrates via workspace Undo. It refuses encrypted PDFs, XFA/hybrid documents, signature fields and document certification permissions. This is **partial**: authorization/password/security settings remain enforced, and clean installed Windows acceptance remains outstanding.

- **Booklet imposition (native)**: `pdfBooklet.ts` plans correct saddle-stitch front/back page order (padding to multiples of four) and embeds original vector artwork into two-up landscape PDF pages, with PDF reopen tests and strict refusal of forms, signatures, annotations, links, outlines and rotated pages. This is **partial**: right-to-left binding, bleed/crop marks, printer physical imposition and Windows duplex-print acceptance remain unverified.

- **Local PDF preflight / inert JavaScript inspection**: `pdfPreflight.ts` scans bounded, parseable PDF object graphs, inventories page/field/annotation counts, identifies direct or indirect JavaScript entries without executing them, and emits JSON reports. Stream-backed JavaScript is flagged as uninspected instead of decoded. These satisfy **partial** `verify-pdf` and `show-javascript` functionality, not veraPDF conformance, trusted cryptographic validation, or a full malware/scripting scan. Windows application acceptance pending.

- **Markdown → PDF**: `markdownToPdf.ts` implements offline, bounded, page-wrapped PDF document generation from Markdown headings, lists, code fences, quotes and paragraphs. It refuses malformed UTF-8 and resource-intensive outputs and makes unsupported Unicode visible as escapes. This is **partial** conversion parity pending richer Markdown types, images, real font embedding and packaged Windows PDF save/reopen acceptance.

- **Local PDF API developer diagnostics**: `pdfApiManual.ts` exports a bounded, redacted JSON inventory of actual loaded PDF provider routes, required fields, capability-gated status and components. No secret field defaults, executable paths, uploaded files or runtime messages are included. It is **partial** `dev-api-docs` support, not a hosted API reference, and does not claim any live route executed successfully. Windows application export acceptance pending.

- **PDF visual signature mark**: `pdfVisualSignature.ts` adds a typed, plainly non-cryptographic name mark at a bounded page location, with safeguards against rewriting signed/certified PDFs, real reopen test, and Undo-safe UI integration. This is **partial** `sign` support: it does not generate PKCS#7/PFX signatures, trusted timestamps, pen/handwriting capture or certificate identity evidence; installed Windows visual placement acceptance pending.

- **File → PDF (.txt)**: `plainTextToPdf.ts` renders literal UTF-8 text into a searchable, paginated PDF locally, without executing HTML or Markdown markup. Source and output sizes, page counts and malformed UTF-8 are bounded and tested. This is **partial** `file-to-pdf` support only: Office formats (DOCX/ODT/XLSX/PPTX etc.) still require lawful offline provider integration and clean Windows export acceptance.

- **EML → PDF (text-only)**: `emlToPdf.ts` parses bounded UTF-8/ASCII MIME messages with decoded text/plain and multipart/alternative bodies into a reopened searchable PDF, treating all message content as inert text. HTML-only messages, attachments, malformed MIME, and unsupported charset encodings are explicitly refused rather than silently dropping material or fetching remote content. It remains **partial**: full MIME/attachment and HTML reconstruction, installed Windows acceptance and license review remain outstanding.

- **PDF → PowerPoint (rasterized PPTX)**: `pdfToPresentation.ts` packages rendered PDF pages into a genuine OpenXML PPTX slide-master/slide-layout/theme graph with per-slide PNG image relationships. It preserves page order and aspect ratio, validates PNG and package structure, enforces limits, and is exposed in local PDF tools. It is **partial** parity: it does not create editable slide text/vector objects, and real Windows PowerPoint/LibreOffice opening and export acceptance remain outstanding.

- **Nested PDF table-of-contents editing**: `pdfOutlineTree.ts` supports bounded read/append, nested child creation, title changes, sibling reorder and guarded subtree deletion of real PDF /Outlines. Named page targets and closed outline branches survive, malformed/cyclic trees and signed/XFA/certified documents are refused, and Undo integration is wired to Organize. This is **partial** pending clean installed Windows acceptance, richer cross-parent reorder and explicit named destination edits.
